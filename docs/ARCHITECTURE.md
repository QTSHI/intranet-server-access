# 架构与工作方式

这个方案把只能从内网连接的 Linux SSH 服务器，接入一个可通过 HTTPS 使用的网页工作台。公网 VPS 运行网页和 SSH 网关；能够访问目标服务器的路由器或其他内网设备，主动向 VPS 建立反向 SSH 转发。

```mermaid
flowchart LR
  B[浏览器] -->|HTTPS / WebSocket| N[VPS Nginx]
  N -->|127.0.0.1:8090| A[Node.js 工作台]
  A -->|127.0.0.1:22002| R[VPS 反向转发监听]
  L[内网路由器 / 中转设备] -->|主动建立 SSH 连接| R
  R -->|经既有 SSH 隧道| L
  L -->|内网 SSH| S[192.168.50.10:22]
```

图中的地址都是部署示例。反向转发在逻辑上把 VPS 的 `127.0.0.1:22002` 接到内网设备可访问的 `192.168.50.10:22`；VPS 不需要直接路由到该内网地址。

## 一次连接的过程

1. 浏览器打开 `https://lab.example.com/`，加载自托管的终端和编辑器资源。
2. 成员填写目标 Linux 服务器上自己的用户名和密码，浏览器建立 WebSocket 并提交本次认证。
3. 工作台连接固定的本地转发端口，先核对目标 SSH 服务器的 ED25519 主机公钥，再进行个人账户认证。
4. 认证成功后，工作台在该 SSH 连接中打开 PTY 终端，并尝试打开 SFTP。终端和文件操作复用同一个个人账户连接。
5. 浏览器关闭或会话结束时，工作台释放该个人 SSH 连接。设备到 VPS 的反向隧道是独立连接，可继续为其他成员提供通道。

## 三种身份

| 身份 | 用途 | 凭据保管位置 |
| --- | --- | --- |
| VPS 中转账户 `lab_relay` | 让内网设备建立指定端口的反向转发 | 内网设备持有专用 SSH 私钥；VPS 配置其公钥 |
| 目标 Linux 个人账户 | 打开成员自己的终端和文件 | 成员在网页中输入自己的用户名和密码 |
| 目标 SSH 主机身份 | 确认转发到预期服务器 | VPS 工作台保存经过核验的 ED25519 公钥 |

成员不共享中转账户登录目标服务器。目录访问、文件读写和终端权限由目标 Linux 账户决定；文件概览从个人主目录开始，也能访问该账户有权限的共享路径。

## 工作台功能

- **终端**：xterm.js 显示远端 PTY 输出，支持键盘输入、调整尺寸及全屏。原终端保留 Tab 补全和 Vim 等交互方式。
- **快速输入**：可收起的本地单行输入栏。文字编辑即时完成，Enter 将整行和回车发送到当前终端，随后焦点回到终端。它不生成预测回显，也不保存命令历史。
- **文件概览**：通过同一条个人 SSH 连接中的 SFTP 列出目录、读取文本文件。
- **多标签编辑**：CodeMirror 支持多文件草稿、语法高亮、查找替换和保存。草稿保存在当前页面内存中。
- **保存**：仅修改已有的 UTF-8 普通文件，单文件最多 256 KiB。保存前后核对版本，在同目录写入临时文件并保留属性，再通过 OpenSSH POSIX rename 扩展原子替换。
- **连接诊断**：分别显示浏览器到网页网关的往返、SFTP 文件状态请求耗时和终端处理排队。它们是不同阶段的采样，不能相加当作实测按键回显时间。

SFTP 不可用时，终端仍能使用。保存需要目标 SFTP 服务支持 POSIX rename；SFTP v3 不提供真正的比较并交换，最终复查与替换之间仍有外部并发修改窗口。

## 网络前提

内网设备必须已经能够连接目标服务器，也必须能够访问 VPS 的 SSH 端口。它可以位于目标局域网，也可以运行或借助已有的校园网、VPN 或专线通道。

反向 SSH 转发只复用这条已有的可达路径，不负责登录校园 VPN，也不会自动让任意设备进入内网。目标 SSH 不需要直接监听公网；VPS 上的反向转发端口只绑定回环地址。

## 会话与数据边界

工作台的固定目标在服务端配置，浏览器不能改成任意 SSH 主机。WebSocket 校验完整 Origin，并保留认证失败限流、连接数量限制和输出回压。应用仅监听回环地址，由 Nginx 提供 HTTPS 并覆盖真实客户端 IP 请求头。

网页服务负责转交本次 SSH 认证，属于凭据经过的可信系统。应用不将密码、命令历史、终端输出或文件正文写入日志；草稿也不写入浏览器持久存储。刷新、关闭页面或返回登录后，未保存的草稿不会保留。

公网网关和反向隧道都可能影响交互延迟。快速输入改善本地文字编辑手感；远端执行、补全和输出仍要等待网络。需要长时间运行的任务可在目标服务器中使用 `tmux`、`screen` 或其他任务管理方式。
